# Symfony fixture

A real Symfony application, used as the large end-to-end target for elephc: it is what
`--web` and `bin/console` compilation are measured and verified against.

**`vendor/` and `var/` are not in git.** They are reinstallable, they are Symfony's code rather
than this repository's, and one build artefact under `public/` once grew past GitHub's 100 MB
blob limit and blocked every push. What IS tracked is the 26 files that define the fixture —
the controller, the routes, the templates, and the two lock files that pin exact versions.

## Restore it

Requires **PHP >= 8.4** (developed against 8.5.10) with `ext-ctype` and `ext-iconv`, plus
[Composer](https://getcomposer.org/).

```sh
cd examples/symfony-app
composer install          # honours composer.lock, so you get the exact pinned versions
APP_ENV=prod APP_DEBUG=0 php bin/console cache:warmup
```

`composer install` — not `composer update`. `composer.lock` and `symfony.lock` are tracked
precisely so that everyone compiles the same tree; updating them changes what the compiler is
being tested against.

Check it before involving elephc at all:

```sh
APP_ENV=prod APP_DEBUG=0 php -d variables_order=EGPCS -S 127.0.0.1:8000 -t public public/index.php
curl -s http://127.0.0.1:8000/plain     # -> "hello from a compiled controller"
```

`php -S` on this fixture is also the reference every elephc measurement is compared against,
byte for byte and interleaved for latency. It answers in ~1.3 ms on the development machine.

## Routes

`/` renders a Twig template; `/plain`, `/greet/{name}` and `/echo` (GET and POST) are plain
responses. `/no-such-route` exercises the 404 path, which reaches Symfony's `ErrorHandler` and
is the route most likely to find a missing builtin.

**The default environment is `dev`** (`.env` says `APP_ENV=dev`), and in `dev` this app's routes
are not wired: `php -S` itself answers 404 on every one of them. That is correct behaviour, not
a defect — pass `APP_ENV=prod APP_DEBUG=0` to exercise the routes.

## Compiling it with elephc

```sh
# from the repository root, not from here
./target/release/elephc --web --timings \
  --ini opcache.preload=$PWD/examples/symfony-app/elephc-preload.php \
  examples/symfony-app/public/index.php
```

Two traps, both of which have cost real time:

- **`--ini opcache.preload=FILE` is ignored unless FILE is already reachable from the entry's
  statically-resolved include graph.** The compiler warns once and continues, and the warning is
  easy to miss in a build log with hundreds of lines. When it is ignored the DI container is not
  compiled, the interpreter covers it silently, and the binary still answers every route
  byte-identically — roughly 2.3x slower. Check the binary's size and that it carries the
  container before trusting any measurement.
- **`elephc-preload.php` names Twig's compiled templates by content hash**, so it must be
  regenerated after any `cache:warmup` that changes a template. Stale entries are silently
  skipped.

## What is deliberately not here

`var/cache/**` is generated by `cache:warmup` and is environment-specific; `vendor/**` comes from
`composer install`. Compiled elephc output (`public/index*`, `*.s`, `*.o`) is build debris — a
single `.s` for this app is over a gigabyte, so keep it out of commits.
